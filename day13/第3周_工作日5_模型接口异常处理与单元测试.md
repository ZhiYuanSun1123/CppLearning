## 5. 什么是异常

异常用于报告函数无法按照约定完成操作的情况。

例如：

```cpp
InferenceRequest request(
    "",
    "What happened?"
);
```

音频路径为空，无法形成合法请求。构造函数可以：

```cpp
throw std::invalid_argument(
    "音频路径不能为空"
);
```

执行`throw`后：

```text
停止当前正常流程
      ↓
离开当前函数
      ↓
沿调用栈寻找匹配catch
      ↓
进入异常处理代码
```

如果一直找不到匹配的`catch`，程序会调用`std::terminate()`并异常终止。

---

## 6. `std::invalid_argument`

用于调用者提供了不合法参数：

```cpp
if (audio_path.empty()) {
    throw std::invalid_argument(
        "音频路径不能为空"
    );
}
```

适合今天的情况：

- 音频路径为空；
- 问题为空；
- 后端名称为空；
- 某个配置值超出允许范围。

它表达：

> 调用函数的方式不符合接口要求。

---

## 7. `std::runtime_error`

用于参数本身可能合法，但操作在运行时无法完成：

```cpp
if (!backend.is_ready()) {
    throw std::runtime_error(
        "后端未就绪: "
        + backend.name()
    );
}
```

适合：

- 后端未加载；
- 模拟推理失败；
- 文件在运行时无法打开；
- 服务依赖不可用；
- 推理引擎返回失败。

它表达：

> 调用形式可能正确，但运行环境或执行过程失败。

## 9. 按值抛出，按`const`引用捕获

推荐：

```cpp
throw std::invalid_argument(
    "问题不能为空"
);
```

捕获：

```cpp
catch (
    const std::invalid_argument& error
) {
    std::cerr
        << error.what()
        << '\n';
}
```

通用规则：

```text
throw by value
catch by const reference
```

不推荐按值捕获：

```cpp
catch (std::exception error) {
}
```

按值捕获可能复制异常对象，并可能产生异常对象切片。

---

## 10. 捕获顺序

`std::invalid_argument`和`std::runtime_error`都继承自`std::exception`。

应先捕获具体类型，再捕获基础类型：

```cpp
try {
    // 可能抛异常
} catch (
    const std::invalid_argument& error
) {
    std::cerr
        << "Invalid argument: "
        << error.what()
        << '\n';
} catch (
    const std::runtime_error& error
) {
    std::cerr
        << "Runtime error: "
        << error.what()
        << '\n';
} catch (
    const std::exception& error
) {
    std::cerr
        << "Other standard error: "
        << error.what()
        << '\n';
}
```

错误顺序：

```cpp
catch (const std::exception& error) {
}
catch (const std::invalid_argument& error) {
}
```

第一个`catch`已经能捕获`invalid_argument`，后面的具体分支无法发挥作用，编译器可能警告。

## 12. 构造函数抛异常时会发生什么

```cpp
InferenceRequest::InferenceRequest(
    const std::string& audio_path,
    const std::string& question
)
    : audio_path_(audio_path),
      question_(question) {
    if (audio_path_.empty()) {
        throw std::invalid_argument(
            "音频路径不能为空"
        );

}
```

如果抛出异常：

- `InferenceRequest`对象没有构造成功；
- 不会调用`InferenceRequest`自己的析构函数；
- 已经成功构造的成员对象会自动析构；
- 栈展开会清理已经完成构造的局部对象。

这里的`std::string`成员会由C++自动清理，不需要手动释放。

## 13. 析构函数不要抛异常

析构函数通常应保持不抛异常：

```cpp
~ModelBackend() override = default;
```

如果栈展开过程中已经有一个异常，而析构函数又抛出另一个异常，程序可能直接调用：

```cpp
std::terminate()
```

因此：

- 析构函数负责可靠清理；
- 不要从析构函数向外传播异常；
- 清理失败通常记录日志或采用其他不抛异常策略；
- RAII对象的析构应尽量安全。

今天不需要自定义复杂析构函数。

## 15. Arrange、Act、Assert

一个测试通常分为三部分。

### Arrange：准备

```cpp
const InferenceRequest request(
    "meeting.wav",
    "What happened?"
);
```

### Act：执行

```cpp
const std::string path =
    request.audio_path();
```

### Assert：断言

```cpp
runner.expect_equal(
    path,
    "meeting.wav",
    "request stores audio path"
);
```

结构：

```text
Arrange
准备输入和对象
      ↓
Act
执行被测试操作
      ↓
Assert
比较实际结果和预期结果
```

---

## 16. 为什么不只使用`assert`

C标准断言：

```cpp
#include <cassert>

assert(actual == expected);
```

适合简单实验，但有两个限制：

- 第一次失败就终止，后面的测试不会继续；
- 定义`NDEBUG`后，`assert`可能被移除。

今天实现一个很小的`TestRunner`，让所有测试运行完并汇总结果。

## 17. 轻量测试运行器

```cpp
class TestRunner {
public:
    void expect_true(
        bool condition,
        const std::string& test_name
    ) {
        if (condition) {
            ++passed_;

            std::cout
                << "[PASS] "
                << test_name
                << '\n';
        } else {
            ++failed_;

            std::cerr
                << "[FAIL] "
                << test_name
                << '\n';
        }
    }

    void expect_equal(
        const std::string& actual,
        const std::string& expected,
        const std::string& test_name
    ) {
        if (actual == expected) {
            ++passed_;

            std::cout
                << "[PASS] "
                << test_name
                << '\n';
        } else {
            ++failed_;

            std::cerr
                << "[FAIL] "
                << test_name
                << '\n'
                << "  expected: "
                << expected
                << '\n'
                << "  actual:   "
                << actual
                << '\n';
        }
    }

    void expect_equal(
        int actual,
        int expected,
        const std::string& test_name
    ) {
        if (actual == expected) {
            ++passed_;

            std::cout
                << "[PASS] "
                << test_name
                << '\n';
        } else {
            ++failed_;

            std::cerr
                << "[FAIL] "
                << test_name
                << '\n'
                << "  expected: "
                << expected
                << '\n'
                << "  actual:   "
                << actual
                << '\n';
        }
    }

    int finish() const {
        std::cout
            << "\nPassed: "
            << passed_
            << "\nFailed: "
            << failed_
            << '\n';

        return failed_ == 0 ? 0 : 1;
    }

private:
    int passed_ = 0;
    int failed_ = 0;
};
```

今天出现了同名函数：

```cpp
expect_equal(string, string, string)
expect_equal(int, int, string)
```

这是函数重载。编译器根据参数类型在编译期选择版本，属于静态多态。

运算符重载仍留到第4周系统学习。

## 19. 测试异常路径

```cpp
void test_empty_audio_path(
    TestRunner& runner
) {
    bool received_expected_exception =
        false;

    try {
        const InferenceRequest request(
            "",
            "What happened?"
        );

        static_cast<void>(request);
    } catch (
        const std::invalid_argument& error
    ) {
        received_expected_exception =
            std::string(error.what()).find(
                "音频路径"
            ) != std::string::npos;
    } catch (...) {
        received_expected_exception =
            false;
    }

    runner.expect_true(
        received_expected_exception,
        "empty audio path throws invalid_argument"
    );
}
```

这里：

```cpp
catch (...)
```

只用于测试兜底，表示如果抛出了其他类型，测试不通过。

```cpp
static_cast<void>(request);
```

用于明确表示这个局部对象只用于触发构造，不需要读取，避免某些未使用变量警告。今天会用即可，类型转换在后续再系统复习。

## 20. 为什么测试异常类型

下面两个行为并不完全相同：

```cpp
throw std::invalid_argument(
    "音频路径不能为空"
);
```

```cpp
throw std::runtime_error(
    "音频路径不能为空"
);
```

文本相同，但错误分类不同。

如果接口约定无效参数应抛：

```cpp
std::invalid_argument
```

测试就应该验证类型，以防实现以后错误地改成另一种异常。

## 21. 不可用模拟后端

为了测试：

```cpp
if (!backend.is_ready())
```

创建一个只在测试文件使用的派生类：

```cpp
class UnavailableBackend
    : public ModelBackend {
public:
    UnavailableBackend()
        : ModelBackend(
              "UnavailableBackend"
          ) {
    }

    bool is_ready() const override {
        return false;
    }

    InferenceResult infer(
        const InferenceRequest& request
    ) const override {
        return InferenceResult(
            name(),
            "Unexpected inference: "
                + request.audio_path()
        );
    }

```

这个类不是产品功能，而是可控测试替身。

它让测试稳定地制造：

```text

```

而不需要关闭网络、损坏真实模型或修改生产类。

## 23. 让服务变得容易测试

你当前`InferenceService::run()`返回：

```cpp
void
```

并在内部直接打印结果。这样测试只能截获终端输出，比较麻烦。

建议改成返回`InferenceResult`：

```cpp
class InferenceService {
public:
    InferenceResult run(
        const ModelBackend& backend,
        const InferenceRequest& request
    ) const;
};
```

实现：

```cpp
InferenceResult InferenceService::run(
    const ModelBackend& backend,
    const InferenceRequest& request
) const {
    if (!backend.is_ready()) {
        throw std::runtime_error(
            "后端未就绪: "
            + backend.name()
        );
    }

    return backend.infer(request);
}
```

正常应用中：

```cpp
const InferenceResult result =
    service.run(
        backend,
        request
    );

result.print();
```

测试中：

```cpp
const InferenceResult result =
    service.run(
        backend,
        request
    );

runner.expect_equal(
    result.backend_name(),
    "Whisper",
    "service returns backend name"
);
```

原则：

> 核心逻辑返回结构化结果，界面层决定如何输出，通常比核心逻辑内部直接打印更容易测试。

## 26. 测试静态调用计数

不要假设计数测试开始时一定是0，因为其他测试可能已经调用过后端。

错误测试：

```cpp
backend.infer(request);

runner.expect_equal(
    WhisperBackend::inference_count(),
    1,
    "count is one"
);
```

如果之前已经调用过，测试会受到顺序影响。

更稳定的方式：

```cpp
void test_whisper_count(
    TestRunner& runner
) {
    const int before =
        WhisperBackend::inference_count();

    const WhisperBackend backend(
        "Whisper"
    );

    const InferenceRequest request(
        "meeting.wav",
        "What happened?"
    );

        backend.infer(request);

        WhisperBackend::inference_count();

        after,
        before + 1,
        "Whisper count increases by one"
    );
}
```

这验证的是行为：

```text
一次调用使计数增加1
```

而不是依赖全局执行顺序。

## 27. 测试矩阵

|测试对象|正常路径|边界/无效输入|运行失败|
|---|---|---|---|
|`InferenceRequest`|保存路径和问题|空路径、空问题|不适用|
|`InferenceResult`|保存并返回结果|空结果是否允许由接口约定决定|不适用|
|`ModelBackend`|合法名称|空名称|不适用|
|`WhisperBackend`|返回Whisper结果|合法请求边界|模拟内部失败可用测试替身|
|`QwenOmniBackend`|返回Qwen结果|合法请求边界|模拟内部失败可用测试替身|
|`InferenceService`|调用可用后端|不适用|后端未就绪、推理异常|
|运行时多态|两个后端通过基类引用调用|不适用|异常仍通过基类接口传播|
|静态计数|调用后增加1|测试顺序变化|不应影响异常前后的接口约定|

## 33. 异常安全基础

今天只需认识三个层次。

### 不泄漏资源

函数失败后，已经构造的RAII对象会被清理。

### 基本保证

异常发生后，对象仍然有效，可以安全析构，但状态可能发生允许范围内的变化。

### 强保证

操作失败后，对象状态与调用前相同。

### 不抛异常保证

函数承诺不会向外抛异常，常用`noexcept`表达。

今天的核心要求是：

- 不泄漏资源；
- 对象保持有效；
- 析构函数不向外抛异常；
- 不盲目给可能分配字符串的函数添加`noexcept`。

## 34. 常见错误

### 错误1：所有错误都抛`runtime_error`

无效参数更适合：

```cpp
std::invalid_argument
```

### 错误2：按值捕获异常

```cpp
catch (std::exception error)
```

推荐：

```cpp
catch (const std::exception& error)
```

### 错误3：先捕获父类异常

```cpp
catch (const std::exception&)
catch (const std::invalid_argument&)
```

具体类型应排在前面。

### 错误4：只测试正常路径

构造函数的参数校验必须有对应异常测试。

### 错误5：测试只打印、不判断

```cpp
std::cout << result.output();
```

这需要人工判断，不是自动测试。

### 错误6：服务只打印结果

返回结构化结果更容易测试：

```cpp
InferenceResult run(...);
```

### 错误7：异常测试只检查“发生过异常”

还应检查是否为约定的异常类型。

### 错误8：测试依赖静态计数初始值为0

使用调用前后差值。

### 错误9：测试程序永远返回0

失败时必须返回非0。

### 错误10：测试中调用真实模型

今天使用可控模拟后端，测试应快速、稳定、可重复。

## 47. 今天结束时应该真正理解的内容

异常处理不是：

```text
在main外面套一个try/catch
```

而是：

```text
接口规定失败类型
      ↓
底层在合适位置报告失败
      ↓
中间层决定传播还是处理
      ↓
边界层转换为用户可理解的信息
```

单元测试也不是：

```text
运行程序没有崩溃
```

而是：

```text
给定明确输入
      ↓
执行一个可控行为
      ↓
自动比较实际结果和预期结果
      ↓
失败时提供定位信息
```

今天最终形成：

```text
统一ModelBackend接口
        ├── 正常Whisper后端
        ├── 正常Qwen后端
        ├── 不可用测试后端
        └── 执行失败测试后端
                 ↓
        InferenceService
                 ↓
     正常、边界、异常、多态测试
```

这才是一个可以继续扩展的模型接口练习项目。
