## 1. “从空目录构建”是什么意思

这里的“空目录”主要指一个全新的构建目录，而不是没有源码的目录。

项目源码已经存在：

```text
cpp-project-template/
├── CMakeLists.txt
├── CMakePresets.json
├── include/
├── src/
├── app/
└── tests/
```

但开始构建之前不存在：

```text
build/
```

执行 CMake 后才生成：

```text
build/
├── debug/
└── release/
```

这能验证项目没有偷偷依赖：

- 旧的 `CMakeCache.txt`；
- 以前生成的目标文件；
- IDE 私有配置；
- 写死在构建目录里的绝对路径；
- 手工复制进去但没有写入构建规则的文件。

因此，可靠的验证方式是：

```bash
rm -rf build
cmake --preset debug
cmake --build --preset debug
ctest --preset debug
```

`rm -rf build` 会删除构建产物，执行时必须确认当前目录正确。今天不要求你频繁使用它；理解“全新构建目录验证”这个原则即可。

## 4. CMakeLists.txt 的四类职责

为了避免 CMake 指令混在一起，今天按职责理解它们。

### 4.1 描述项目

```cmake
cmake_minimum_required(VERSION 3.21)

project(
    AudioCppTemplate
    VERSION 0.1.0
    LANGUAGES CXX
)
```

- `cmake_minimum_required`：规定最低 CMake 版本；
- `project`：声明项目名称、版本和使用的语言。

### 4.2 创建目标

```cmake
add_library(audio_core
    src/audio_clip.cpp
)

add_executable(audio_demo
    app/main.cpp
)
```

目标可以理解为 CMake 管理的构建单位。

这里有两个主要目标：

- `audio_core`：库；
- `audio_demo`：可执行程序。

测试开启后还会创建：

```cmake
add_executable(audio_core_tests
    tests/audio_clip_test.cpp
)
```

### 4.3 配置目标

```cmake
target_include_directories(audio_core
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
)

target_compile_features(audio_core
    PUBLIC
        cxx_std_17
)
```

它们分别表示：

- 编译 `audio_core` 及其使用者时应在哪里找公开头文件；
- `audio_core` 以及使用它的目标至少需要 C++17。

```cmake
set_target_properties(audio_core PROPERTIES
    CXX_EXTENSIONS OFF
)
```

它属于“设置目标如何编译”，用于关闭编译器私有的语言扩展，尽量使用标准 C++17。

### 4.4 连接目标

```cmake
target_link_libraries(audio_demo
    PRIVATE
        AudioCppTemplate::audio_core
        project_warnings
)
```

含义是：

- `audio_demo` 使用 `audio_core`；
- `audio_demo` 同时继承 `project_warnings` 提供的警告选项；
- `PRIVATE` 表示这些要求不继续传播给 `audio_demo` 的使用者。

目标关系可以画成：

```text
project_warnings ──> audio_core ──> audio_demo
                              └──> audio_core_tests
```

### 4.5 添加测试

```cmake
include(CTest)

if(BUILD_TESTING)
    include(FetchContent)

    FetchContent_Declare(
        googletest
        URL https://github.com/google/googletest/archive/refs/tags/v1.17.0.tar.gz
    )

    FetchContent_MakeAvailable(googletest)
endif()
```

这里的作用是：

1. 引入 CTest；
2. 仅在 `BUILD_TESTING=ON` 时准备测试；
3. 首次配置时下载 GoogleTest；
4. 创建并注册测试程序。

> 超纲提示：`FetchContent` 的下载缓存、离线依赖管理和企业级包管理暂时不展开。今天只要求会使用模板，并知道首次配置通常需要网络。

## 5. project_warnings 为什么是 INTERFACE 库

```cmake
add_library(project_warnings INTERFACE)
```

它不是包含 `.cpp` 文件的普通代码库，而是一个“构建配置集合”。

```cmake
target_compile_options(project_warnings
    INTERFACE
        -Wall
        -Wextra
        -Wpedantic
)
```

`INTERFACE` 表示：

- `project_warnings` 自己没有源码可以编译；
- 链接它的目标会获得这些编译选项。

因此：

```cmake
target_link_libraries(audio_core PRIVATE project_warnings)
```

会让 `audio_core` 使用这些警告选项。

这不是在链接一个真正包含机器码的库，而是在复用一组构建要求。

## 6. CMakePresets.json 完整讲解

### 6.1 Preset 到底是什么

`CMakePresets.json` 是保存在项目根目录中的 CMake 配置文件。

它把团队反复使用的命令参数保存成带名字的预设。例如，下面这条完整命令：

```bash
cmake \
    -S . \
    -B build/debug \
    -G "Unix Makefiles" \
    -DCMAKE_BUILD_TYPE=Debug \
    -DBUILD_TESTING=ON
```

可以保存为名为 `debug` 的配置预设。以后只需要执行：

```bash
cmake --preset debug
```

Preset 不会取代 `CMakeLists.txt`：

```text
CMakeLists.txt
    描述项目中有哪些目标，以及目标如何编译和连接

CMakePresets.json
    描述一次构建使用什么目录、生成器和配置参数
```

例如：

- `add_library(audio_core ...)` 应写在 `CMakeLists.txt`；
- `Debug 构建放在 build/debug` 应写在 `CMakePresets.json`。

### 6.2 为什么项目需要 Preset

如果每个人手写命令，可能出现：

```text
开发者 A：build 目录是 build/
开发者 B：build 目录是 out/
开发者 C：忘记打开 BUILD_TESTING
开发者 D：使用 Release，却以为自己在运行 Debug
```

Preset 能把常用配置固化到仓库中，使本地开发、IDE 和 CI 尽量使用相同参数。

但它不能保证所有机器环境完全相同。例如，机器仍然需要安装兼容版本的 CMake、编译器和构建工具。

文件：

```json
{

  "configurePresets": [

      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "BUILD_TESTING": "ON"
      }
    },
    {
      "name": "release",
      "displayName": "Release build",
      "generator": "Unix Makefiles",
      "binaryDir": "${sourceDir}/build/release",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Release",
        "BUILD_TESTING": "ON"
      }
    }
  ],
  "buildPresets": [
    {
      "name": "debug",
      "configurePreset": "debug",
      "jobs": 4
    },
    {
      "name": "release",
      "configurePreset": "release",
      "jobs": 4
    }
  ],
  "testPresets": [
    {
      "name": "debug",
      "configurePreset": "debug",
      "output": {
        "outputOnFailure": true
      }
    },
    {
      "name": "release",
      "configurePreset": "release",
      "output": {
        "outputOnFailure": true
      }
    }
  ]
}
```

注意：这是 JSON，不是 CMake 语言：

- 属性名和字符串必须使用双引号；
- 不支持在文件中随意写 `//` 注释；
- 最后一个元素后面不能多写逗号；
- `{}` 表示对象，`[]` 表示数组。

### 6.4 顶层 version

```json
"version": 3
```

它表示这个 Preset 文件使用第 3 版 JSON 结构规范，不是项目版本，也不是 CMake 本身的版本。

两者不要混淆：

```text
"version": 3
    CMakePresets.json 文件格式版本

project(VERSION 0.1.0)
    你的 C++ 项目版本
```

### 6.5 cmakeMinimumRequired

```json
"cmakeMinimumRequired": {
  "major": 3,
  "minor": 21,
  "patch": 0
}
```

表示读取该 Preset 文件至少需要 CMake 3.21.0。

它与 `CMakeLists.txt` 中的：

```cmake
cmake_minimum_required(VERSION 3.21)
```

保持一致。

如果本机版本太低，可以检查：

```bash
cmake --version
```

### 6.6 configurePresets：配置阶段预设

```json
"configurePresets": [
  {
    "name": "debug",
    "displayName": "Debug build",
    "generator": "Unix Makefiles",
    "binaryDir": "${sourceDir}/build/debug",
    "cacheVariables": {
      "CMAKE_BUILD_TYPE": "Debug",
      "BUILD_TESTING": "ON"
    }
  }
]
```

它回答的是：

> CMake 应该如何配置这个项目，并把生成文件写到哪里？

执行方式：

```bash
cmake --preset debug
```

下面逐项解释。

#### name

```json
"name": "debug"
```

机器使用的唯一名称，命令行中的 `debug` 就来自这里：

```bash
cmake --preset debug
```

#### displayName

```json
"displayName": "Debug build"
```

给人看的名称，IDE 可以显示它。它不用于命令行匹配。

#### generator

```json
"generator": "Unix Makefiles"
```

指定 CMake 生成哪种底层构建系统。

这里生成 Makefile，所以之后 `cmake --build` 最终会调用 `make` 完成编译。

常见生成器还有：

```text
Unix Makefiles
Ninja
Xcode
Visual Studio
```

今天使用 `Unix Makefiles` 是为了与你当前的 macOS 命令行环境保持直接、清晰的关系。

> 超纲提示：Ninja 在很多大型工程和 CI 中也很常见，但今天不要求切换生成器。

#### binaryDir

```json
"binaryDir": "${sourceDir}/build/debug"
```

指定构建目录。

`${sourceDir}` 是 CMake Preset 提供的宏，表示包含 `CMakePresets.json` 的项目源码根目录。

假设源码根目录是：

```text
/Users/zhubulandeshuizhuyu/Project/Code/C++/CppLearning/day33/cpp-project-template
```

那么最终目录为：

```text
/Users/zhubulandeshuizhuyu/Project/Code/C++/CppLearning/day33/cpp-project-template/build/debug
```

这相当于命令中的：

```bash
-B build/debug
```

Debug 和 Release 使用不同目录非常重要，因为它们拥有不同的缓存、编译选项和目标文件。

#### cacheVariables

```json
"cacheVariables": {
  "CMAKE_BUILD_TYPE": "Debug",
  "BUILD_TESTING": "ON"
}
```

它们会写入该构建目录的 CMake Cache。

相当于：

```bash
-DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
```

`CMAKE_BUILD_TYPE=Debug`：

- 生成 Debug 配置；
- 通常保留调试信息；
- 通常不开启激进优化；
- 更适合 GDB/LLDB、Sanitizer 和定位错误。

`BUILD_TESTING=ON`：

- 打开 CTest 提供的测试开关；
- 使 `if(BUILD_TESTING)` 内部的 GoogleTest 目标被创建。

如果将其改为：

```json
"BUILD_TESTING": "OFF"
```

那么应用和库仍可构建，但 `audio_core_tests` 不会生成。

### 6.7 release 配置预设

```json
{
  "name": "release",
  "displayName": "Release build",
  "generator": "Unix Makefiles",
  "binaryDir": "${sourceDir}/build/release",
  "cacheVariables": {
    "CMAKE_BUILD_TYPE": "Release",
    "BUILD_TESTING": "ON"
  }
}
```

它和 Debug 的主要差异只有：

| 项目 | Debug | Release |
|---|---|---|
| 构建目录 | `build/debug` | `build/release` |
| 构建类型 | `Debug` | `Release` |
| 主要用途 | 调试和开发 | 优化后运行和发布验证 |

因此执行：

```bash
cmake --preset release
```

不会覆盖 Debug 构建，而会单独生成 `build/release`。

### 6.8 buildPresets：构建阶段预设

```json
"buildPresets": [
  {
    "name": "debug",
    "configurePreset": "debug",
    "jobs": 4
  }
]
```

它回答的是：

> 已经配置好以后，应该构建哪个构建目录，并使用多少并行任务？

执行方式：

```bash
cmake --build --preset debug
```

#### configurePreset

```json
"configurePreset": "debug"
```

表示这个构建预设对应名为 `debug` 的配置预设。

CMake 会由此知道构建目录是：

```text
build/debug
```

不是重新执行配置阶段，而是引用配置预设的信息，找到已经生成的构建树。

#### jobs

```json
"jobs": 4
```

最多并行执行 4 个构建任务，大致相当于：

```bash
cmake --build build/debug --parallel 4
```

它不是“使用 4 个线程运行你的程序”，而是构建时最多并行编译多个源文件。

### 6.9 testPresets：测试阶段预设

```json
"testPresets": [
  {
    "name": "debug",
    "configurePreset": "debug",
    "output": {
      "outputOnFailure": true
    }
  }
]
```

它回答的是：

> 应该在哪个构建目录运行测试，测试失败时如何显示结果？

执行方式：

```bash
ctest --preset debug
```

`configurePreset` 让 CTest 找到 `build/debug`。

```json
"outputOnFailure": true
```

表示测试失败时显示测试程序的标准输出和错误输出。

它大致相当于：

```bash
ctest --test-dir build/debug --output-on-failure
```

如果测试成功，CTest 只显示简洁结果；如果失败，才展开更详细的信息，便于定位断言失败或异常。

### 6.10 三类 Preset 的关系

必须区分三个阶段：

```text
configurePreset
    读取 CMakeLists.txt
    生成 build/debug 中的构建系统
            ↓
buildPreset
    编译源码并链接目标
            ↓
testPreset
    运行已经构建好的测试程序
```

对应命令：

```bash
cmake --preset debug
cmake --build --preset debug
ctest --preset debug
```

它们虽然都叫 `debug`，但属于三个不同数组，因此是三个不同对象：

```text
configurePresets 中的 debug
buildPresets 中的 debug
testPresets 中的 debug
```

使用相同名字只是为了便于记忆，不是必须同名。真正建立关联的是：

```json
"configurePreset": "debug"
```

### 6.11 为什么不能直接执行 buildPreset

在一个真正全新的项目中，如果 `build/debug` 还没有生成，直接执行：

```bash
cmake --build --preset debug
```

通常会失败，因为构建阶段所需的 Makefile 还不存在。

第一次必须先配置：

```bash
cmake --preset debug
```

当你只修改 `.cpp` 或 `.hpp` 后，通常可以直接重新构建：

```bash
cmake --build --preset debug
```

当你修改 `CMakeLists.txt` 后，保险的执行顺序是：

```bash
cmake --preset debug
cmake --build --preset debug
```

### 6.13 CMakePresets.json 与 CMakeUserPresets.json

常见的两个文件是：

```text
CMakePresets.json
CMakeUserPresets.json
```

区别：

| 文件 | 用途 | 是否通常提交 Git |
|---|---|---|
| `CMakePresets.json` | 团队共享配置 | 是 |
| `CMakeUserPresets.json` | 个人机器配置 | 通常否 |

例如某个开发者本机的特殊 SDK 路径、私人编译器路径，不应该写死在团队共享文件中，可以放入个人 Preset。

> 超纲提示：Preset 继承、条件表达式、环境变量和 toolchain 文件属于后续扩展。今天先掌握配置、构建、测试三类 Preset。

### 6.14 修改模板时最常改哪些位置

创建普通新项目时，通常只需要考虑：

```json
"generator": "Unix Makefiles"
"binaryDir": "${sourceDir}/build/debug"
"CMAKE_BUILD_TYPE": "Debug"
"BUILD_TESTING": "ON"
"jobs": 4
```

- 想换 Ninja：修改 `generator`，前提是已安装 Ninja；
- 想换构建目录：修改 `binaryDir`；
- 不构建测试：将 `BUILD_TESTING` 改为 `OFF`；
- 调整并行数量：修改 `jobs`；
- 增加 ASan 配置：后续可以新建一个 `asan` Preset。

不要在 `CMakePresets.json` 中写：

- 库由哪些 `.cpp` 组成；
- 应用链接哪个库；
- 公开头文件在哪里；
- 哪些测试用例需要注册。

这些仍属于 `CMakeLists.txt`。

## 12. 常见错误定位

### 12.1 找不到头文件

```text
fatal error: 'audio_toolkit/audio_clip.hpp' file not found
```

检查：

- `target_include_directories` 是否配置在正确的库目标上；
- `include` 路径是否正确；
- `#include` 是否与目录结构一致。

### 12.2 Undefined symbols

```text
Undefined symbols for architecture arm64
```

常见原因：

- 只声明了函数，没有实现；
- 实现文件没有加入 `add_library`；
- 可执行程序没有通过 `target_link_libraries` 链接库；
- 声明和实现的函数签名不一致。

### 12.3 CMake 找不到源码

```text
Cannot find source file
```

检查 `add_library` 或 `add_executable` 中的相对路径是否从当前 `CMakeLists.txt` 所在目录计算。

### 12.4 测试数量为零

```text
No tests were found
```

检查：

- `BUILD_TESTING` 是否开启；
- 是否调用 `gtest_discover_tests`；
- 测试目标是否成功构建；
- 是否在正确的构建目录运行 CTest。

### 12.5 改了 CMakeLists 但行为没有变化

可能仍在使用旧缓存。先重新执行：

```bash
cmake --preset debug
cmake --build --preset debug
```

若仍然怀疑缓存，再确认目录后删除对应构建目录并重新配置。

### 12.6 FetchContent 下载失败

GoogleTest 首次配置通常需要访问 GitHub。网络失败时，不是 C++ 代码错误。可以：

- 检查网络；
- 稍后重试；
- 使用系统已安装的 GoogleTest；
- 后续学习 Conan 或 vcpkg 管理依赖。

后两项属于后续扩展，今天不要求完成。
