## 7. `AudioMetadata`设计

文件：`include/audio_metadata.hpp`

至少包含：

```cpp
struct AudioMetadata {
    std::string path;
    int sample_rate;
    int channels;
    double duration_seconds;
    std::string label;
    double quality_score;
};
```

字段约束：

```text
path             非空
sample_rate      > 0
channels         > 0
duration_seconds > 0
label            非空
quality_score    位于[0.0, 1.0]
```

今天使用 `struct`是因为它主要表示一条数据记录；约束由索引类的添加和更新接口统一检查。

## 8. 为什么路径作为主键

当前简化项目假设：

```text
一条规范化路径唯一对应一条音频记录
```

因此路径可以作为唯一键：

```cpp
std::unordered_map<std::string, AudioMetadata>
```

优点：

- 按路径精确查找平均 `O(1)`；
- 重复路径容易检测；
- 更新和删除可以先定位主记录。

限制：

- 同一文件不同写法可能被当作不同键；
- 相对路径和绝对路径需要明确策略；
- 文件移动后键会变化；
- 真实系统可能使用稳定ID而不是路径。

今天明确采用字符串规范化后的路径作为主键，不扩展数据库ID。

---

## 9. 路径规范化边界

今天只做轻量字符串规则，例如：

- 去除首尾空白；
- 把扩展名 `.WAV`统一成 `.wav`；
- 明确是否把反斜杠转换为斜杠；
- 拒绝空字符串。

不要声称仅凭字符串处理就完成了真实文件系统规范化。

以下问题属于后续：

- `..`和符号链接；
- 大小写敏感文件系统；
- 绝对路径；
- 文件是否真实存在；
- 权限；
- Unicode规范化。

项目报告必须写明你的规范化规则。

## 10. 主索引

建议：

```cpp
using PrimaryIndex =
    std::unordered_map<std::string, AudioMetadata>;
```

内部成员概念：

```cpp
PrimaryIndex by_path_;
```

只要求会使用类型别名，不深入模板。

主索引负责拥有元数据对象。其他辅助索引不再保存另一份完整 `AudioMetadata`，避免多份数据互相不一致。

---

## 11. 标签辅助索引

一个标签对应多条路径：

```text
speech -> meeting.wav
speech -> interview.wav
music  -> music.wav
```

建议结构：

```cpp
std::unordered_map<
    std::string,
    std::set<std::string>
> paths_by_label_;
```

值保存路径集合，而不是 `AudioMetadata*`。

优点：

- 自动去重路径；
- 删除和一致性检查直观；
- 不长期保存指向主索引元素的裸指针；
- 主索引发生重新哈希时不需要维护指针关系。

代价是查询标签后还需要按路径回主索引取记录。

---

## 12. 采样率辅助索引

需要按采样率有序遍历，可以使用：

```cpp
std::map<int, std::set<std::string>>
    paths_by_sample_rate_;
```

这样可以：

- 查询精确采样率；
- 按采样率有序输出；
- 后续扩展范围查询。

如果只需要精确查询、不需要顺序，也可以使用 `unordered_map`。本练习刻意使用 `map`复习有序索引。

---

## 13. 为什么辅助索引保存路径而不是指针

可以保存：

```cpp
const AudioMetadata*
```

但会增加生命周期推理：

- 主记录删除后指针悬空；
- 容器整体销毁后指针悬空；
- 复制索引对象后指针可能指向原对象；
- 更新实现更难验证；
- 测试更复杂。

当前阶段使用主键作为间接引用：

```text
辅助索引保存path
       ↓
回主索引find(path)
       ↓
得到当前记录
```

这是一个刻意偏向正确性和可维护性的设计。

## 15. 返回指针的生命周期

`find_by_path()`可以返回：

```cpp
const AudioMetadata*
```

找不到返回：

```cpp
nullptr
```

调用者必须知道：

- 删除该路径后指针失效；
- 清空或销毁索引后指针失效；
- 对索引进行赋值后旧指针不应继续使用；
- 不应长期缓存内部元素指针。

虽然 `unordered_map`重新哈希不会单独使未删除元素的引用和指针失效，但 API使用者不应依赖内部容器实现细节长期持有指针。

最安全的使用方式：

```text
查询
立即只读使用
不跨越修改索引的操作保存
```

## 16. 添加流程

`add()`建议按顺序完成：

```text
1. 规范化临时副本
2. 校验全部字段
3. 检查主键是否重复
4. 插入主索引
5. 更新标签索引
6. 更新采样率索引
7. 返回成功
```

必须选择明确的重复策略：

```text
重复路径 -> add返回false，不覆盖旧记录
```

不能悄悄覆盖，否则辅助索引可能仍保留旧标签和旧采样率。

---

## 17. 更新是最容易出错的操作

假设旧记录：

```text
meeting.wav label=speech sample_rate=16000
```

更新为：

```text
meeting.wav label=meeting sample_rate=48000
```

不能只修改主索引：

```cpp
by_path_[path] = replacement;
```

否则辅助索引会变成：

```text
speech仍包含meeting.wav
16000仍包含meeting.wav
```

正确逻辑：

```text
校验replacement
找到旧记录
确认新路径策略
从旧标签索引删除路径
从旧采样率索引删除路径
修改主记录
向新标签索引加入路径
向新采样率索引加入路径
```

如果允许更新路径，复杂度会进一步增加。今天建议：

> `update(path, replacement)`要求 `replacement.path`规范化后仍等于原path；修改路径使用删除再添加。

---

## 18. 空辅助集合要清理

删除标签中的路径后：

```cpp
label_iterator->second.erase(path);
```

如果集合为空，应继续删除标签键：

```cpp
if (label_iterator->second.empty()) {
    paths_by_label_.erase(label_iterator);
}
```

否则会留下：

```text
speech -> 空集合
```

虽然不一定导致崩溃，但会使 `contains label`和统计语义混乱。

采样率辅助索引同理。

---

## 19. 删除流程

建议顺序：

```text
1. 在主索引find(path)
2. 不存在则返回false
3. 读取旧label和sample_rate
4. 从标签索引删除path
5. 清理空标签集合
6. 从采样率索引删除path
7. 清理空采样率集合
8. 最后删除主索引元素
9. 返回true
```

为什么先读取旧字段？

因为主记录删除后：

```cpp
iterator->second
```

就不能继续访问。

可以先复制必要的标签和采样率，再删除。

## 20. 异常安全边界

多个容器的更新不是天然原子的。如果主索引插入成功，而辅助索引插入过程中内存分配抛异常，可能得到不一致状态。

今天的最低要求：

- 所有业务校验在修改容器前完成；
- 正常成功和正常失败路径保持一致；
- 每个公开修改操作后测试 `validate_consistency()`；
- 在报告中承认多容器更新的异常安全限制。

加分做法：

- 先准备可能抛异常的临时数据；
- 记录已经完成的步骤；
- 失败时回滚；
- 或重建辅助索引恢复一致性。

完整事务和强异常保证属于后续工程内容，不要求今天一次解决。

## 21. `validate_consistency()`检查什么

至少检查双向关系。

### 主索引到辅助索引

对每条主记录：

```text
对应标签集合必须包含path
对应采样率集合必须包含path
```

### 辅助索引到主索引

对标签索引中的每条路径：

```text
主索引必须存在
主记录label必须等于当前标签
```

对采样率索引同理。

### 空集合

```text
辅助索引中不允许保存空路径集合
```

复杂度可能是线性的，适合测试、调试和离线检查，不一定每个线上请求都调用。

## 22. 查询结果为什么返回 `vector`

标签或采样率可能匹配多条数据：

```cpp
std::vector<AudioMetadata>
```

优点：

- 调用方容易遍历和排序；
- 返回值拥有自己的元素；
- 后续修改索引不会使结果悬空；
- 容易传给标准算法。

缺点：

- 需要复制元数据；
- 大结果可能增加内存和时间。

当前学习项目优先安全清晰。未来可考虑返回ID、迭代器范围或分页查询。

## 29. 复杂度分析

设记录数为 `n`，单标签或采样率匹配路径数为 `k`。

| 操作 | 预期复杂度 |
|---|---:|
| 按路径查询 | `unordered_map`平均 `O(1)`，最坏 `O(n)` |
| 添加主记录 | 平均 `O(1)`，另加辅助索引成本 |
| 删除主记录 | 平均 `O(1)`，另加集合删除成本 |
| 按标签找路径集合 | 平均 `O(1)` |
| 标签结果回主索引 | 平均约 `O(k)` |
| 按采样率找集合 | `O(log m)`，`m`为采样率键数 |
| 全量一致性检查 | 至少线性级别 |
| 结果排序 | `O(k log k)` |

这些是容器操作的理论趋势，不包含字符串复制、哈希计算和内存分配常数成本。

## 30. 失效规则在项目中的应用

### `unordered_map`重新哈希

- 旧迭代器失效；
- 未删除元素引用和指针不会仅因重新哈希失效；
- 但项目不鼓励长期缓存内部指针。

### `erase()`

- 被删除元素的迭代器、引用和指针失效；
- 辅助索引必须同步删除路径。

### 返回 `vector`查询结果

- 结果拥有副本；
- 不依赖索引内部元素生命周期；
- 结果自身执行 `push_back/erase`时仍遵循 `vector`失效规则。

## 31. 复制与移动语义提醒

如果 `AudioMetadataIndex`只包含标准容器，编译器生成的复制通常可以复制数据内容，而且辅助索引保存的是字符串键，不是内部裸指针，因此比指针索引更安全。

但要明确：

- 复制一个大型索引成本可能很高；
- 返回整个索引不是好接口；
- 测试复制行为不是今天强制要求；
- 后续可根据业务决定允许复制、只允许移动或使用共享服务对象。

## 32. 常见错误

### 错误1：使用 `operator[]`只查询

可能意外插入空记录或空集合。查询使用 `find()`或 `at()`。

### 错误2：重复添加时覆盖主索引

辅助索引可能仍保留旧字段。

### 错误3：更新只修改主索引

标签和采样率索引变脏。

### 错误4：先删除主记录再读取旧标签

迭代器已经失效。

### 错误5：删除路径后不清理空集合

辅助索引语义混乱。

### 错误6：辅助索引复制完整元数据

产生多份真相，更新容易不一致。

### 错误7：辅助索引长期保存内部裸指针

删除和复制时生命周期复杂。

### 错误8：查询不存在标签时使用 `operator[]`

会创建一个空标签键。

### 错误9：返回内部引用后调用方长期保存

删除、清空或对象销毁后悬空。

### 错误10：没有测试失败路径

只验证正常添加不足以证明索引可靠。

### 错误11：认为ASan能发现辅助索引不一致

这是业务逻辑错误，必须通过一致性测试发现。

### 错误12：测试依赖 `unordered_map`遍历顺序

顺序不受保证。

## 52. 最终速记

```text
主索引：unordered_map<path, AudioMetadata>

标签索引：unordered_map<label, set<path>>

采样率索引：map<sample_rate, set<path>>

辅助索引保存主键，不复制完整记录，不长期保存内部裸指针

add：先校验，再改状态

update：移除旧辅助关系，修改主记录，添加新辅助关系

remove：先读旧字段，清辅助索引，最后删主记录

查询：find，不用operator[]制造数据

一致性：主到辅、辅到主双向检查

测试：成功、失败、状态转换、边界、一致性、Sanitizer

音频元数据工具不等于音频硬件或音频解码系统
```
