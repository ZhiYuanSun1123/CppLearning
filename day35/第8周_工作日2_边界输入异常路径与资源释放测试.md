## 3. 先分清正常、边界、非法输入

当前构造函数的约定是：

```text
path 非空
sample_rate > 0
channels > 0
frame_count >= 0（类型是 size_t，本来就不能表示负数）
```

根据这份约定分类：

| 输入 | 分类 | 预期行为 |
|---|---|---|
| 16000 Hz、1 声道、32000 帧 | 常规正常值 | 构造成功，时长 2 秒 |
| 0 帧 | 合法边界 | 构造成功，时长 0 秒 |
| 1 Hz、1 声道、1 帧 | 最小合法正值 | 构造成功，时长 1 秒 |
| 0 Hz 或 -1 Hz | 非法输入 | 抛 `std::invalid_argument` |
| 0 或 -1 声道 | 非法输入 | 抛 `std::invalid_argument` |
| 空路径 | 非法输入 | 抛 `std::invalid_argument` |

“边界”不等于“错误”。边界是允许范围的端点或刚好跨越端点的值。

通常围绕一个条件选择：

```text
条件：sample_rate > 0

-1：端点外的非法值
 0：刚好非法的端点
 1：最小合法值
```

这叫边界值分析的基本思路。今天不追求所有整数极值，也不要为了凑数量随便写几十个相同测试。

### 3.1 为什么 0 帧是合法的

一个刚创建、尚未收到音频帧的流可以暂时为空。当前业务约定允许它：

```cpp
const audio_toolkit::AudioClip clip("empty.wav", 16000, 1, 0);
EXPECT_EQ(clip.frame_count(), std::size_t{0});
EXPECT_DOUBLE_EQ(clip.duration_seconds(), 0.0);
```

如果未来业务改成“持久化音频必须至少一帧”，约定和测试应一起修改。测试不是独立于需求的真理，它把当前约定变成可执行检查。

### 3.2 为什么 frame_count 不测负数

它的类型是 `std::size_t`，属于无符号整数。写：

```cpp
AudioClip("a.wav", 16000, 1, -1);
```

负数会先隐式转换成一个非常大的无符号值，并不代表“成功传入负帧数”。今天不要用这个写法冒充负数输入测试。如果接口需要区分负数并给出异常，应改用能表达负值的参数类型再验证。

## 4. 异常路径测试

### 4.1 基本写法

```cpp
EXPECT_THROW(
    static_cast<void>(audio_toolkit::AudioClip("a.wav", 0, 1, 10)),
    std::invalid_argument
);
```

含义：执行第一项语句，预期它抛出能被 `std::invalid_argument` 捕获的异常。

`static_cast<void>(临时对象)` 的作用是明确表达“只执行构造以观察是否抛异常，不需要保存对象”，也避免某些未使用结果警告。它不改变异常行为，也不负责释放资源；临时对象若构造成功会按 C++ 生命周期规则析构。

常用异常断言：

```cpp
EXPECT_THROW(statement, ExceptionType);
ASSERT_THROW(statement, ExceptionType);
EXPECT_ANY_THROW(statement);
EXPECT_NO_THROW(statement);
```

| 断言 | 检查内容 |
|---|---|
| `EXPECT_THROW` | 必须抛出指定类型或可按该类型捕获的异常 |
| `ASSERT_THROW` | 同上，失败后停止当前测试函数 |
| `EXPECT_ANY_THROW` | 只要抛异常即可，不关心类型 |
| `EXPECT_NO_THROW` | 不应抛出任何异常 |

业务代码能够区分参数错误、运行失败时，优先检查具体异常类型，不要一律使用 `EXPECT_ANY_THROW`。

### 4.2 为什么一项测试要覆盖 0 和 -1

```cpp
TEST(AudioClipExceptionTest, RejectsZeroAndNegativeSampleRate) {
    EXPECT_THROW(/* sample rate = 0 */, std::invalid_argument);
    EXPECT_THROW(/* sample rate = -1 */, std::invalid_argument);
}
```

两次断言表达同一个行为：“非正采样率被拒绝”。这比为两个相邻输入复制两个几乎相同的文件更紧凑，也符合你要求的综合练习方式。

但不要把路径、采样率、声道数所有非法值全部塞进一个测试。它们是不同规则，失败时应能从测试名快速定位。

### 4.3 检查错误消息

`EXPECT_THROW` 主要确认异常类型，不直接检查 `what()`。需要检查原因时写：

```cpp
try {
    static_cast<void>(audio_toolkit::AudioClip("a.wav", 0, 1, 10));
    FAIL() << "expected std::invalid_argument";
} catch (const std::invalid_argument& error) {
    EXPECT_EQ(std::string(error.what()), "sample rate must be positive");
} catch (...) {
    FAIL() << "expected std::invalid_argument, but caught another type";
}
```

执行顺序：

1. 若构造正确抛出 `invalid_argument`，进入第一个 catch，检查消息。
2. 若完全没有抛异常，会走到 `FAIL()`，当前测试发生致命失败。
3. 若抛出其他类型，进入 `catch (...)` 并失败。

`FAIL()` 是 GoogleTest 的致命失败宏，会结束当前测试函数。`error.what()` 返回 `const char*`，这里先转换成 `std::string` 再使用 `EXPECT_EQ` 比较内容。

是否严格比较整段错误文字取决于项目约定。内部错误消息经常调整时，过度严格会使测试脆弱；对外 API 承诺固定消息或错误码时，精确检查才更有价值。本例用于学习异常原因定位。

### 4.4 不要在异常断言里做太多事

不推荐：

```cpp
EXPECT_THROW(load_config(), std::runtime_error);
```

如果 `load_config()` 内部同时读文件、解析、联网和分配资源，失败时你很难知道是哪一步。单元测试应尽量让一项行为和一个原因可定位。

## 5. 资源释放为什么需要专门测试

“函数返回值正确”不代表资源一定释放。文件句柄、socket、模型 session、GPU buffer 都可能在异常路径被漏掉。

今天用下面三个计数模拟：

```cpp
struct ResourceState {
    int active_count{0};
    int acquire_count{0};
    int release_count{0};
};
```

- `active_count`：当前仍处于占用状态的资源数量；
- `acquire_count`：总共成功获取过几次；
- `release_count`：总共释放过几次。

正常结束后期望：

```text
active_count  = 0
acquire_count = 1
release_count = 1
```

只检查 `active_count == 0` 还不充分。如果代码从未获取资源，它也为 0；所以还要验证确实获取了一次，也恰好释放一次。

### 5.1 为什么观察状态使用 shared_ptr

若计数状态是 `TrackedResource` 自身的普通成员，资源对象析构后测试也无法访问它。这里让资源对象和测试共同持有 `ResourceState`：

```text
测试 ──shared_ptr──┐
                  ├── ResourceState
资源 ──shared_ptr──┘
```

资源释放会销毁资源对象持有的那一个 `shared_ptr`，但测试仍持有状态，因此可以读取释放后的计数。

这是对**状态对象**的共享所有权，不代表真实文件句柄或 GPU 资源由两边共同释放。真实资源的释放职责仍由 `TrackedResource` 独占表达。

### 5.2 正常作用域退出

```cpp
const auto state = std::make_shared<ResourceState>();
{
    const AudioSession session(state, "qwen-omni");
    EXPECT_EQ(state->active_count, 1);
}
EXPECT_EQ(state->active_count, 0);
EXPECT_EQ(state->release_count, 1);
```

花括号创建一个更小作用域。离开作用域时 `session` 析构，其 `resource_` 成员随之析构并更新计数。

不要在对象还活着时就期望 `active_count == 0`。

## 6. 构造函数抛异常时谁会析构

`AudioSession` 的成员声明顺序：

```cpp
TrackedResource resource_;
std::string model_name_;
```

构造过程：

```text
1. 构造 resource_，获取模拟资源
2. 构造 model_name_
3. 进入 AudioSession 构造函数体
4. 检测到 fail_after_acquire，抛异常
```

异常发生后：

```text
AudioSession 整体没有构造成功
    ├── 不调用 ~AudioSession()
    ├── 已构造的 model_name_ 被析构
    └── 已构造的 resource_ 被析构 → 资源释放
```

因此参考测试写：

```cpp
EXPECT_THROW(
    static_cast<void>(AudioSession(state, "broken-model", true)),
    std::runtime_error
);

EXPECT_EQ(state->active_count, 0);
EXPECT_EQ(state->acquire_count, 1);
EXPECT_EQ(state->release_count, 1);
```

这正是 RAII 在异常路径上的价值：已成功构造的成员会自动展开销毁，不需要在每个 `catch` 中手工写 release。

### 6.1 如果 resource_ 自己构造失败呢

传入 `nullptr` 时，`TrackedResource` 在增加计数之前抛异常。它自己没有构造成功，因此也不会执行其析构函数；但因为资源尚未获取，不存在需要释放的资源。

```cpp
EXPECT_THROW(
    static_cast<void>(AudioSession(nullptr, "model")),
    std::invalid_argument
);
```

这说明“没有调用析构”不总是泄漏。关键要问：异常发生前，资源是否已经成功获得并交给某个已构造完成的 RAII 对象管理。

## 11. 使用 Sanitizer 验证

CMake 已加入 `asan` preset：

```bash
cmake --preset asan
cmake --build --preset asan
ctest --preset asan
```

它为本项目启用：

```text

-fno-omit-frame-pointer
```

- AddressSanitizer 关注越界、use-after-free 等可检测内存错误；具体平台是否提供完整泄漏检测要看工具链。
- UndefinedBehaviorSanitizer 关注部分未定义行为。
- GoogleTest 计数断言检查我们规定的资源获取/释放协议。

“测试全通过”和“Sanitizer 没报告”都只能说明本次执行到的路径没有触发相应问题，不能证明所有输入、所有平台和所有并发场景绝对安全。

本例的 `TrackedResource` 没有裸 `new/delete`，ASan 零报告并不能替代 acquire/release 计数测试。反过来，计数正确也不能证明代码没有数组越界。两种检查关注点不同。

## 13. 今天测试能保证什么、不能保证什么

### 可以验证

- 当前指定边界输入的行为；
- 当前非法输入抛出指定异常类型；
- 一项指定错误消息；
- 模拟资源在正常和构造失败路径中各释放一次；
- 这些路径在本机构建配置下能够运行。

### 不能保证

- 所有可能整数极值都安全；
- 真实文件、socket、GPU 和模型句柄一定正确释放；
- 多线程同时访问时安全；
- 没有尚未执行到的内存错误；
- 业务流程完整，比如真实音频被成功解码或推理回答正确。

RAII 保证的是：当管理对象正常析构时执行析构逻辑，并在栈展开中销毁已完成构造的自动对象和成员。它不能保证：

- `std::abort`、强制杀进程等不执行栈展开的路径也调用析构；
- 析构函数内部写错的释放逻辑自动变正确；
- 资源释放就等于业务事务完成；
- 外部系统操作自动回滚。

## 14. 常见错误排查

| 表现 | 检查位置 |
|---|---|
| 预期异常但没有抛 | 输入是否真的违反构造约定 |
| 抛了异常但类型不对 | 测试预期类型与实际 throw 类型 |
| `what()` 比较失败 | 消息拼写、空格、实际进入了哪个检查 |
| active 已经是 0 | 是否在资源对象仍存活的作用域外检查 |
| release 为 0 | RAII 成员是否构造成功、析构是否更新状态 |
| release 大于 acquire | 是否重复释放或多个测试共用状态 |
| 测试显示 SKIPPED | 仍保留 `GTEST_SKIP()`，练习尚未完成 |
| 找不到测试 | 是否开启 BUILD_TESTING 并重新构建正确目录 |
| 改完仍是旧结果 | 是否重新 `cmake --build`，是否运行了正确 preset 的程序 |
| ASan 构建链接报符号错误 | 编译和链接阶段是否都带 sanitizer 选项；本项目 target 已统一处理 |

不要用 `try { ... } catch (...) { SUCCEED(); }` 测特定异常，它会让错误异常类型也通过。

不要为了让测试通过而删除业务验证。先确认需求和测试是否正确，再修改实现。
