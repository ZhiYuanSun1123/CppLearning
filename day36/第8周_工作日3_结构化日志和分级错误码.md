## 3. 为什么普通文本日志不够

普通文本：

```text
模型失败了 req-42 model unavailable
```

人能大致看懂，但程序不知道哪部分是请求 ID、错误码或消息。不同人还可能写出不同格式。

结构化日志：

```json
{"timestamp":"2026-09-02T09:00:00+08:00","level":"ERROR","event":"inference_failed","request_id":"req-42","error_code":3001,"error_name":"model_unavailable","category":"model","message":"model is unavailable"}
```

固定字段允许日志平台：

- 按 `request_id` 串联一次请求；
- 统计 `error_code=3001` 出现次数；
- 筛选 `level=ERROR`；
- 按 `category=model` 聚合；
- 解析时间并排序。

“结构化”核心不是一定使用 JSON，而是字段及含义稳定。JSON Lines 是常见形式：每条日志独占一行，每一行都是完整 JSON 对象。

## 4. 日志字段设计

```cpp
struct LogRecord {
    std::string timestamp;
    LogLevel level{LogLevel::info};
    std::string event;
    std::string request_id;
    ErrorCode error_code{ErrorCode::ok};
    std::string message;
};
```

| 字段 | 作用 | 示例 |
|---|---|---|
| timestamp | 事件时间，建议带时区 | `2026-09-02T09:00:00+08:00` |
| level | 严重程度 | `INFO`、`ERROR` |
| event | 稳定的事件名 | `inference_failed` |
| request_id | 串联一次请求 | `req-42` |
| error_code | 程序稳定识别的数字 | `3001` |
| error_name | 便于人阅读的稳定名称 | `model_unavailable` |
| category | 聚合的大类 | `model` |
| message | 可读说明 | `model is unavailable` |

不要把日志消息本身当唯一错误码。文字可能翻译或调整，程序依赖整段文字会很脆弱。

也不要记录密码、令牌、用户完整音频内容等敏感数据。本例只记录请求 ID 和受控消息；真实项目还需要脱敏与访问控制。

## 5. 日志级别与错误码不是一回事

```cpp
enum class LogLevel { debug, info, warning, error };
```

- 日志级别说明这条记录多严重、是否需要告警。
- 错误码说明具体发生了哪一类业务结果。

相同错误码在不同上下文中可能采用不同级别。例如客户端传空参数，在边缘服务可记 WARNING，在严格内部管道也可能记 ERROR。今天简化为成功记 INFO、失败记 ERROR。

日志级别的常见理解：

| 级别 | 含义 |
|---|---|
| DEBUG | 调试细节，生产环境可能默认关闭 |
| INFO | 正常关键流程 |
| WARNING | 已发生异常情况，但请求或系统仍可继续 |
| ERROR | 当前操作失败，需要定位 |

今天没有 FATAL，因为不同日志库对“记录后是否终止”定义不同，不能只凭名字假设行为。

## 6. 分级错误码设计

```cpp
enum class ErrorCode : int {
    ok = 0,
    invalid_audio_path = 1001,
    invalid_question = 1002,
    audio_not_found = 2001,
    decode_failed = 2002,
    model_unavailable = 3001,
    inference_failed = 3002,
    internal_error = 9001
};
```

本项目约定：

| 范围 | 分类 | 含义 |
|---:|---|---|
| 0 | success | 成功 |
| 1000～1999 | input | 调用者输入问题 |
| 2000～2999 | io | 文件与解码问题 |
| 3000～3999 | model | 模型加载或推理问题 |
| 9000～9999 | internal | 未归类的内部失败 |

编号不是行业统一标准，是本项目的稳定约定。真实公司会有自己的规范。

### 6.1 为什么用 enum class

相较裸整数：

```cpp
return 3001;
```

这样更清楚：

```cpp
return ErrorCode::model_unavailable;
```

`enum class` 作用域更明确，也不会隐式转换为整数。确实要写进 JSON 时显式转换：

```cpp
static_cast<int>(record.error_code)
```

### 6.2 错误码需要稳定

发布后不要让 3001 今天表示模型不可用，明天又表示音频不存在。名称、数字和含义应一起维护。

不要仅依赖千位除法分类，因为未来编号可能有空洞或兼容区间。本例 `error_category()` 显式检查范围，让规则集中在一处。

### 6.3 未知枚举值

调用者可以通过强制转换制造未定义在枚举项中的值：

```cpp
const auto unknown = static_cast<ErrorCode>(7777);
```

所以 `switch` 之后仍返回 `unknown_error`，分类返回 `unknown`。不要假设枚举变量永远只含列出的项。

## 7. 错误码、异常、退出码的区别

| 机制 | 作用范围 | 本项目例子 |
|---|---|---|
| 业务错误码 | 函数/API 结果，调用者可处理 | `model_unavailable=3001` |
| C++ 异常 | 正常返回流程之外的错误传播 | 今天核心服务暂不使用异常 |
| 进程退出码 | 程序结束后通知 shell 成败 | main 成功返回 0，失败返回 1 |

业务错误码 3001 不应该直接作为可移植的进程退出码。很多系统只保留退出码的低位，而且 shell 的约定与 API 错误码不是同一层。

当前 `InferenceService::run()` 把预期内的失败放入 `InferenceResponse`：

```cpp
struct InferenceResponse {
    ErrorCode code;
    std::string answer;
    std::string message;
    bool ok() const noexcept;
};
```

这让调用者能明确分支：

```cpp
if (response.ok()) {
    // 使用 answer
} else {
    // 读取 code 和 message
}
```

异常不是“高级版错误码”，错误码也不是所有异常的替代物。预期的业务失败常适合结果对象；无法在当前层处理的构造失败、违反程序不变量等可能使用异常。实际项目需要统一约定。

## 8. 错误检查顺序会影响结果

服务依次检查：

```text
音频路径是否为空
    ↓
问题是否为空
    ↓
是否模拟文件不存在
    ↓
模型是否可用
    ↓
是否模拟推理失败
    ↓
成功
```

如果一个请求同时路径为空、问题为空，返回 `invalid_audio_path`，因为它先被检查。测试必须按公开约定判断，不要假设能一次返回所有错误。

真实系统也可以返回错误列表，但那是另一种接口设计。本项目使用“返回遇到的第一个错误”。

`missing.wav` 和 `force-failure` 是为了让示例可重复而设置的模拟触发值，并不代表生产代码应该通过文件名或问题文字制造错误。真实实现应调用文件系统和模型后端，并把底层失败映射到本层错误码。

## 9. JSON 为什么必须转义

如果消息是：

```text
model "A"
failed
```

直接拼接会让消息中的双引号和换行破坏 JSON 字符串或一行一条日志的约定。

基础转义：

| 原字符 | JSON 字符串中写成 |
|---|---|
| `"` | `\"` |
| `\` | `\\` |
| 换行 | `\n` |
| 回车 | `\r` |
| 制表符 | `\t` |
| 其他 0x00～0x1F 控制字符 | `\u00xx` 形式 |

`escape_json()` 遍历字符并转换。它服务于今天固定字段的教学生成器，不是完整 JSON 库：

- 不负责解析 JSON；
- 不验证整个输入是否为合法 UTF-8；
- 不处理任意对象层次、数组和数值类型；
- 不提供生产级性能与安全审计。

这也是为什么真实项目优先使用经过测试的库。

### 9.1 为什么测试使用固定时间

测试中写：

```cpp
"2026-09-02T09:00:00+08:00"
```

而不是在 `to_json()` 内直接获取当前时间。固定输入才能得到可重复的精确预期结果。如果函数内部读取系统时钟，每次结果都变，测试会困难。

生产设计常把 clock/time provider 注入日志组件，或先生成 `LogRecord` 再序列化。今天直接让调用者提供 timestamp，先掌握可测试性。

## 10. ostream 注入让日志可测试

```cpp
class StructuredLogger {
public:
    explicit StructuredLogger(std::ostream& output) noexcept;
    void log(const LogRecord& record);
private:
    std::ostream& output_;
};
```

运行程序时传 `std::cout`：

```cpp
StructuredLogger logger(std::cout);
```

测试时传 `std::ostringstream`：

```cpp
std::ostringstream output;
StructuredLogger logger(output);
logger.log(record);
EXPECT_NE(output.str().find("\"error_code\":0"), std::string::npos);
```

同一个类不需要知道输出目标是终端还是内存字符串。测试不必重定向全局 `std::cout`，也不写临时文件。

这里保存 `std::ostream&` 引用，所以外部流必须比 logger 活得久。logger 不拥有和不负责析构该 stream。

## 17. 生产实现还缺少什么

本日版本适合学习和小型项目骨架，但生产环境通常还需要：

- 成熟 JSON 序列化库，而非手工拼字符串；
- spdlog 等成熟日志库；
- 自动时间戳、线程 ID、进程 ID、trace/span ID；
- 日志级别过滤、异步队列和背压策略；
- 文件轮转、保留期限和磁盘容量保护；
- 多线程写入安全；
- 敏感字段脱敏和日志访问权限；
- 错误码文档、负责人及兼容策略；
- 底层错误到公开错误码的映射；
- 指标、追踪与日志关联；
- 写日志失败时的降级策略。

因此简历可以写“实现结构化日志原型及分级错误码，并添加测试”，不能夸大为“实现生产级可观测平台”。

## 18. 常见错误排查

| 问题 | 原因或检查点 |
|---|---|
| JSON 在消息中间断行 | 没把真实换行转义为 `\\n` |
| JSON 引号错位 | message 中双引号未转义 |
| `std::string_view` 乱码 | view 指向已销毁的局部字符串 |
| 错误分类不对 | 数值范围重叠或枚举编号放错区间 |
| 失败 response 仍然 ok | `ok()` 没有只判断 `ErrorCode::ok` |
| CTest 没找到测试 | 没重新 build 或使用了错误 build 目录 |
| 练习显示通过但其实跳过 | 查看 SKIPPED 数量并移除 GTEST_SKIP |
| 输出有两行 | message 未转义或 logger 多写换行 |
| 测试时无法读取日志 | logger 写死 std::cout，没有注入 ostream |
| 退出码与 3001 对不上 | 业务错误码和进程退出码不是同一概念 |
