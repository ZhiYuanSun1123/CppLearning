## 1. 今天只学习两个核心问题

### 问题一：测试结果怎样保存下来

平时运行：

```bash
ctest --preset debug
```

结果只显示在终端中。终端关闭或者输出被覆盖后，不方便保存和交给 GitHub Actions 使用。

今天会生成一个 XML 测试报告：

```text
report/test-results.xml
```

它会记录：

- 测试名称；
- 测试数量；
- 成功或失败；
- 测试耗时；
- 失败信息。

### 问题二：为什么测试有时成功、有时失败

如果代码完全相同，一个测试却出现：

```text
第一次：通过
第二次：通过
第三次：失败
第四次：又通过
```

这个测试称为“不稳定测试”，英文常叫 **flaky test**。

今天的顺序：

```text
先运行稳定测试
    ↓
生成测试报告
    ↓
读懂报告中的主要字段
    ↓
故意加入不稳定测试
    ↓
重复运行以尝试复现
    ↓
分析不稳定原因
    ↓
删除不稳定因素并再次验证
```

## 5. 先区分三种概念

### 5.1 被测程序有错误

例如任务队列错误地让低优先级任务先执行。测试每次都能稳定发现这个错误。

```text
同一代码 + 同一输入 → 每次都失败
```

这通常是业务代码错误。

### 5.2 测试断言写错了

业务代码是正确的，但测试写了错误的期望值。

```cpp
EXPECT_EQ(queue.size(), 100U);
```

测试每次也都会失败，这是测试代码错误，但它仍然是“稳定失败”，不叫 flaky test。

### 5.3 测试不稳定

同一份代码没有修改，结果却可能发生变化：

```text
同一代码 + 看似同一测试 → 有时通过，有时失败
```

原因是测试偷偷依赖了会变化的外部因素。

## 6. 常见的不稳定因素

| 不稳定因素 | 例子 |
|---|---|
| 当前时间 | 断言操作必须在极短时间内完成 |
| 随机数 | 每次随机生成不同输入 |
| 线程执行顺序 | 假设线程 A 永远先于线程 B |
| 网络 | 依赖远程服务器始终可用 |
| 文件顺序 | 假设目录遍历结果固定 |
| 共享状态 | 上一个测试遗留文件或全局变量 |
| 机器性能 | 使用固定 `sleep` 等待异步任务 |

修复的核心不是“多试几次”，而是：

> 找到测试依赖的变化因素，并让输入、环境和期望结果变得确定。

## 8. 生成测试报告

### 8.1 直接执行命令

```bash
mkdir -p report
ctest --test-dir build/debug \
    --output-on-failure \
    --output-junit "$(pwd)/report/test-results.xml"
```

参数解释：

| 参数 | 作用 |
|---|---|
| `--test-dir build/debug` | 到这个构建目录寻找测试 |
| `--output-on-failure` | 失败时显示详细输出 |
| `--output-junit ...` | 将结果保存为 JUnit XML |

`JUnit` 在这里是一种通用测试报告格式，不代表今天改用 Java。CTest、GitHub Actions 和很多测试平台都能使用这种 XML 格式。

这里使用 `"$(pwd)/report/test-results.xml"` 得到绝对路径。原因是使用 `--test-dir build/debug` 后，CTest 对相对输出路径的处理容易让报告落到构建目录中。明确写出绝对路径，可以保证报告出现在 `day38/report`。

### 8.2 使用项目脚本

为了避免每次输入全部命令，我为今天的练习编写了：

[打开 generate-test-report.sh](</Users/zhubulandeshuizhuyu/Project/Code/C++/CppLearning/day38/scripts/generate-test-report.sh>)

运行：

```bash

```

这个脚本不是 CMake 自动生成的，也不是系统内置脚本。它只是依次执行：


## 9. 测试报告怎么看

打开生成的文件：

```text
day38/report/test-results.xml
```

你可能看到类似结构：

```xml
<testsuite name="..." tests="5" failures="0" time="...">
  <testcase name="StartsEmpty" classname="AudioTaskQueueTest" time="..."/>
</testsuite>
```

只需要认识这些字段：

| 字段 | 含义 |
|---|---|
| `tests` | 测试总数 |
| `failures` | 失败数量 |
| `time` | 执行耗时 |
| `testcase` | 一个具体测试 |
| `name` | 测试名称 |
| `classname` | 测试套件名称 |

如果测试失败，相关 `testcase` 中通常会增加 `failure` 内容。

XML 是给工具读取的，终端输出是给人即时查看的。你不需要手工维护这个 XML。

## 10. 什么叫重复运行测试

测试只运行一次并通过，不能证明它没有偶发失败。

CTest 提供：

```bash
ctest --test-dir build/debug \
    --repeat until-fail:50 \
    --output-on-failure
```

含义是：每个测试最多重复 50 次；一旦失败就停止该测试，并显示错误。

项目提供了脚本：

[打开 repeat-tests.sh](</Users/zhubulandeshuizhuyu/Project/Code/C++/CppLearning/day38/scripts/repeat-tests.sh>)

运行：

```bash
bash scripts/repeat-tests.sh 50
```

数字 `50` 是重复次数。它不是“失败后重试到成功”，而是“重复成功的测试，尝试暴露偶发失败”。

## 11. 实验一：故意制造不稳定测试

打开练习：

[01_flaky_test_experiment.md](</Users/zhubulandeshuizhuyu/Project/Code/C++/CppLearning/day38/exercises/01_flaky_test_experiment.md>)

练习会让测试结果依赖当前时钟数值：

```cpp
const auto now = std::chrono::steady_clock::now()
                     .time_since_epoch()
                     .count();
EXPECT_EQ(now % 2, 0);
```

这里没有测试任何业务规则。`now` 每次运行都不同，因此 `now % 2` 也不保证固定。

这个例子唯一的目的，是让你看到“不修改代码，结果仍可能变化”。完成观察后必须删除。

## 12. 实验二：真正修复不稳定测试

打开练习：

[02_fix_flaky_test.md](</Users/zhubulandeshuizhuyu/Project/Code/C++/CppLearning/day38/exercises/02_fix_flaky_test.md>)

错误修复方法包括：

- 失败就重新运行，直到成功；
- 随便增加 `sleep`；
- 注释掉失败测试；
- 放宽断言让错误通过。

真正的修复方法是删除不稳定依赖，并使用：

- 固定输入；
- 明确业务规则；
- 固定期望结果；
- 每个测试独立的状态。

本项目的相同优先级测试就是修复后的确定性形式：

```cpp
queue.push("first.wav", 5);
queue.push("second.wav", 5);
queue.push("third.wav", 5);

EXPECT_EQ(queue.pop_next().path, "first.wav");
EXPECT_EQ(queue.pop_next().path, "second.wav");
EXPECT_EQ(queue.pop_next().path, "third.wav");
```

业务规则规定相同优先级保持提交顺序，所以每次结果都相同。

## 13. GitHub Actions 中怎样保存报告

工作流文件：

[打开 day38-test-report.yml](</Users/zhubulandeshuizhuyu/Project/Code/C++/CppLearning/.github/workflows/day38-test-report.yml>)

它在 day37 的基础上增加两件事。

### 13.1 在云端生成 XML

```yaml
- name: Generate JUnit test report
  working-directory: day38
  run: >-
    ctest --test-dir build/debug
    --output-on-failure
    --output-junit "$GITHUB_WORKSPACE/day38/report/test-results.xml"
```

这与本地生成报告的命令相同。

### 13.2 上传 Artifact

```yaml
- name: Upload test report
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: day38-test-results
    path: day38/report/test-results.xml
    if-no-files-found: error
```

Artifact 可以理解为“本次 CI 运行保存下来的文件”。工作流结束后，可以在 GitHub Actions 运行页面下载它。

`if: always()` 表示前面的测试即使失败，也尽量执行上传步骤。因为测试失败时，报告反而更值得保存。

> `if: always()` 和 Artifact 属于今天第一次出现的 GitHub Actions 知识。需要理解用途，不要求背写法。

## 14. 为什么不应该把生成的 XML 提交到 Git

`.gitignore` 中有：

```text
report/*.xml
report/*.log
```

因为 XML 是每次运行自动生成的结果：

- 内容经常变化；
- 可以随时重新生成；
- 不属于源代码；
- 提交后容易制造无意义差异。

应提交的是生成方法，也就是脚本和工作流；不是每次生成的临时报告。

## 16. 常见问题

### 16.1 找不到 `report/test-results.xml`

检查：

- 是否在 `day38` 目录执行；
- 是否已经成功构建；
- 命令是否包含 `--output-junit`；
- 测试是否在报告生成前就因其他命令失败而中断。

### 16.2 重复 50 次没有发现失败

这不代表测试必然稳定。重复运行只能增加发现问题的机会，不能从数学上证明测试永远稳定。

判断测试是否稳定，还要阅读代码，检查它是否依赖时间、随机数、网络、线程顺序或共享状态。

### 16.3 为什么不直接重试失败测试

如果失败后一直重试，最终成功就算通过，会隐藏真实问题。CI 可能变绿，但程序或测试依然不可靠。

重复运行用于发现不稳定；不能作为掩盖不稳定的长期方案。

### 16.4 脚本是否需要完全学会

今天需要：

- 会运行；
- 知道每个脚本解决什么问题；
- 看懂核心的 `ctest` 命令；
- 脚本失败时会读错误信息。

今天不要求：

- 背 `set -euo pipefail`；
- 背参数校验正则表达式。

Shell 会在后续 Linux 工程内容中逐步补充。
