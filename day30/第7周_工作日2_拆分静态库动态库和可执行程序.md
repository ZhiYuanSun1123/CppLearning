## 3. 从 `.cpp`到可执行程序发生了什么

先看简化流程：

```text
tensor_shape.cpp
        │
        │ 预处理和编译
        ▼
tensor_shape.cpp.o
        │
        │ 与其他目标文件链接
        ▼
可执行程序或库
```

### 源文件

```text
src/tensor_shape.cpp
```

它包含函数定义和实现代码。

### 头文件

```text
include/tensor_shape.hpp
```

它主要提供类、函数和类型声明，让其他翻译单元知道接口是什么。

### 目标文件

macOS中通常看到：

```text
tensor_shape.cpp.o
```

它已经包含机器代码，但通常还不能独立运行。

### 链接

链接器负责把多个目标文件和库中的符号连接起来：

```text
main.cpp.o
tensor_shape.cpp.o
tensor_metadata.cpp.o
        │
        │ 链接
        ▼
tensor_metadata_demo
```

如果只有函数声明而没有链接到实现，可能出现：

```text
Undefined symbols for architecture arm64
```

---

## 4. 什么是符号

可以把函数和全局对象的名称粗略理解为链接器需要解析的符号。

头文件声明：

```cpp
std::string_view to_string(DataType type) noexcept;
```

`main.cpp`调用它时，编译器知道函数签名，但真正实现位于：

```text
src/data_type.cpp
```

链接器要找到对应定义并连接起来。

如果忘记把 `data_type.cpp`加入库target，最终可能链接失败。

---

## 5. 静态库是什么

静态库通常是多个目标文件的归档集合。

macOS和Linux常见扩展名：

```text
.a
```

例如：

```text
libtensor_metadata.a
```

形成过程：

```text
data_type.cpp.o ──────────┐
device.cpp.o ─────────────┤
tensor_layout.cpp.o ──────┤
tensor_shape.cpp.o ───────┼─> libtensor_metadata.a
tensor_metadata.cpp.o ────┘
```

CMake明确创建静态库：

```cmake
add_library(tensor_metadata STATIC
    src/data_type.cpp
    src/device.cpp
    src/tensor_layout.cpp
    src/tensor_shape.cpp
    src/tensor_metadata.cpp
)
```

---

## 6. 静态链接发生了什么

可执行程序链接静态库：

```cmake
target_link_libraries(
    tensor_metadata_demo
    PRIVATE
    tensor_metadata
)
```

构建时：

```text
main.cpp.o
    +
libtensor_metadata.a中需要的目标代码
    ↓
tensor_metadata_demo
```

程序需要的库代码会在链接阶段进入最终可执行程序。

注意，更准确地说，链接器通常从静态库中提取需要的目标文件或符号，并不保证把整个静态库所有代码原样复制进去。

运行时通常不再需要原来的：

```text
libtensor_metadata.a
```

因此静态库的基本特点是：

- 部署相对简单；
- 可执行文件通常更大；
- 多个程序可能各自包含一份库代码；
- 更新静态库后需要重新链接程序；
- 不容易出现“运行时找不到这个 `.a`”的问题。

---

## 7. 动态库是什么

动态库保存可以在程序加载或运行时被装入的共享代码。

不同平台扩展名：

```text
macOS：.dylib
Linux：.so
Windows：.dll
```

本机示例：

```text
libtensor_metadata.dylib
```

CMake明确创建动态库：

```cmake
add_library(tensor_metadata SHARED
    src/data_type.cpp
    src/device.cpp
    src/tensor_layout.cpp
    src/tensor_shape.cpp
    src/tensor_metadata.cpp
)
```

---

## 8. 动态链接发生了什么

构建可执行程序时，它不会像静态链接那样把所有所需实现直接放入自己的文件，而会记录动态依赖信息。

```text
tensor_metadata_demo
        │
        │ 记录依赖
        ▼
libtensor_metadata.dylib
```

程序启动时，macOS动态加载器负责找到并加载动态库。

因此动态库的基本特点是：

- 可执行文件通常更小；
- 多个程序可以使用同一个动态库；
- 系统可能共享动态库的只读代码页；
- 运行时必须能找到动态库；
- 更新库时要考虑二进制兼容；
- 部署需要处理路径和版本。

如果动态库无法找到，程序可能启动失败，而不是等到调用某个函数才一定失败。

---

## 9. 静态库与动态库对比

|对比项|静态库|动态库|
|---|---|---|
|macOS文件|`.a`|`.dylib`|
|CMake类型|`STATIC`|`SHARED`|
|库代码进入程序的时机|链接阶段|加载或运行阶段|
|运行时是否需要库文件|通常不需要原 `.a`|需要 `.dylib`|
|可执行文件大小|通常较大|通常较小|
|部署复杂度|相对低|相对高|
|更新库|通常重新链接程序|ABI兼容时可替换|
|多程序共享|各程序通常包含所需代码|可共同使用动态库|
|常见问题|体积、重复代码|搜索路径、版本、ABI|

“通常”非常重要。最终大小和装载行为还会受链接器优化、系统库、调试信息和构建模式影响。

---

## 10. 为什么两种库都需要头文件

头文件解决的是编译阶段问题：

```text
有哪些类型？
函数参数是什么？
返回值是什么？
类有哪些成员？
```

库文件解决的是链接或运行阶段问题：

```text
函数的机器代码实现在哪里？
```

所以：

```text
头文件 + 静态库
```

以及：

```text
头文件 + 动态库
```

都是常见组合。

只有头文件而没有实现库，可能链接失败；只有库而没有接口声明，普通C++代码也不知道如何正确调用。

## 11. 可执行程序是什么

```cmake
add_executable(
    tensor_metadata_demo
    app/main.cpp
)
```

创建可执行target。

它通过：

```cmake
target_link_libraries(
    tensor_metadata_demo
    PRIVATE
    tensor_metadata
)
```

依赖库target。

不管 `tensor_metadata`最终是静态库还是动态库，消费者仍然链接逻辑target名称：

```text
tensor_metadata
```

Demo不用硬编码：

```text
libtensor_metadata.a
libtensor_metadata.dylib
```

这是CMake target抽象的重要价值。

---

## 12. INTERFACE库不属于这两种二进制库

```cmake
add_library(project_warnings INTERFACE)
```

它不生成：

```text
.a
.dylib
.o
```

它只保存和传播构建要求，例如：

```text
-Wall
-Wextra
-Wpedantic
```

所以不要把：

```text
STATIC / SHARED
```

和：

```text
INTERFACE配置target
```

当成完全相同的产物类型。

## 14. 两种实现方案

### 方案A：同一target，通过构建选项切换

```cmake
add_library(tensor_metadata
    src/data_type.cpp
    src/device.cpp
    src/tensor_layout.cpp
    src/tensor_shape.cpp
    src/tensor_metadata.cpp
)
```

这里没有明确写 `STATIC`或 `SHARED`。

然后使用：

```cmake
option(
    BUILD_SHARED_LIBS
    "Build libraries as shared libraries"
    OFF
)
```

配置时决定：

```bash
-DBUILD_SHARED_LIBS=OFF
```

生成静态库；

```bash
-DBUILD_SHARED_LIBS=ON
```

生成动态库。

这是今天推荐的核心方案。

### 方案B：同时建立两个不同target

```cmake
add_library(tensor_metadata_static STATIC ...)
add_library(tensor_metadata_shared SHARED ...)
```

优点是一个build目录同时生成两种库，缺点是：

- 相同源码通常会编译两次；
- 两个target需要重复或抽取配置；
- 消费者需要明确选择链接哪个target；
- 初学阶段更容易混淆target名称与输出名称。

今天先掌握方案A，方案B作为扩展。

## 15. `BUILD_SHARED_LIBS`到底是什么

它是CMake约定使用的变量。

当你写：

```cmake
add_library(tensor_metadata
    src/tensor_metadata.cpp
)
```

但没有写库类型时：

```text
BUILD_SHARED_LIBS=OFF
    默认创建STATIC库

BUILD_SHARED_LIBS=ON
    默认创建SHARED库
```

如果你已经明确写了：

```cmake
add_library(tensor_metadata STATIC ...)
```

那么 `BUILD_SHARED_LIBS=ON`也不会把它改成动态库，因为 `STATIC`已经明确指定。

---

## 16. 为什么要使用两个build目录

错误方向是反复在同一个缓存目录切换：

```bash
cmake -B build -DBUILD_SHARED_LIBS=OFF
cmake -B build -DBUILD_SHARED_LIBS=ON
```

虽然可以重新配置，但你无法同时保留和比较两套产物，也容易被缓存干扰。

推荐：

```text
day30/build-static
day30/build-shared
```

分别配置：

```bash
cmake \
  -S day27 \
  -B day30/build-static \
  -DCMAKE_BUILD_TYPE=Debug \
  -DBUILD_SHARED_LIBS=OFF
```

```bash
cmake \
  -S day27 \
  -B day30/build-shared \
  -DCMAKE_BUILD_TYPE=Debug \
  -DBUILD_SHARED_LIBS=ON
```

两套构建互不覆盖。

## 22. 使用 `otool -L`查看动态依赖

检查静态版可执行程序：

```bash
otool -L \
  day30/build-static/tensor_metadata_demo \
  > day30/report/static-dependencies.txt
```

检查动态版：

```bash
otool -L \
  day30/build-shared/tensor_metadata_demo \
  > day30/report/shared-dependencies.txt
```

动态版应列出类似：

```text
@rpath/libtensor_metadata.dylib
```

静态版不会把 `libtensor_metadata.a`列为运行时动态依赖，因为它所需代码已经在链接阶段进入可执行程序。

但是静态版仍然可能列出系统动态库，例如C++标准库。这不表示你的 `tensor_metadata`静态链接失败。

## 23. `rpath`是什么

动态版程序启动时需要找到：

```text
libtensor_metadata.dylib
```

可执行文件中可能记录：

```text
@rpath/libtensor_metadata.dylib
```

`rpath`可以理解为：

> 动态加载器寻找动态库时使用的一组运行时搜索路径。

CMake在build目录中通常会设置合适的构建期rpath，让刚构建的Demo能够找到同一构建树里的动态库。

今天只要求：

- 能从 `otool -L`看到动态依赖；
- 知道动态库必须在运行时可定位；
- 知道源码include路径不能解决动态库加载问题。

今天不要求手写复杂的安装rpath。

---

## 24. include路径、链接路径和运行时路径不能混淆

### include路径

解决编译器找头文件：

```cmake
target_include_directories(...)
```

### 链接依赖

解决链接器使用哪个库target：

```cmake
target_link_libraries(...)
```

### 运行时动态库路径

解决程序启动时去哪里找 `.dylib`：

```text
rpath
install_name
动态加载器搜索规则
```

所以即使：

```text
头文件能找到
代码能编译
程序能链接
```

动态库路径错误仍然可能导致程序启动失败。


你会看到经过C++名称修饰的符号。

今天只需要知道：

- 库向链接器或加载器提供符号；
- 声明与定义签名不一致会导致找不到符号；
- C++符号名称通常会经过name mangling。

不要求今天系统学习目标文件格式。

## 28. 什么是PIC

PIC是Position Independent Code，即位置无关代码。

动态库可能被加载到不同虚拟地址，因此其机器代码通常需要适合重定位和共享。

CMake对 `SHARED`库通常会自动启用：

```text
POSITION_INDEPENDENT_CODE
```

今天不需要手动添加：

```text
-fPIC
```

如果以后要把静态库目标文件再次链接进动态库，可能需要为静态库启用PIC：

```cmake
set_target_properties(
    some_static_library
    PROPERTIES
    POSITION_INDEPENDENT_CODE ON
)
```

这是进阶内容，不加入今天核心验收。

## 29. 动态库更新为什么涉及ABI

API主要是源码层面接口，例如：

```cpp
std::size_t rank() const noexcept;
```

ABI涉及已经编译后的二进制如何互相调用，例如：

- 符号名称；
- 参数传递方式；
- 类内存布局；
- 虚函数表布局；
- 编译器和标准库兼容性。

即使头文件看起来修改不大，替换动态库也可能破坏已有程序的二进制兼容性。

所以“动态库可以直接替换更新”必须加前提：

> 新动态库与已有消费者保持ABI兼容。

今天只要求理解这个风险，不要求设计稳定ABI。

## 32. 自己的模块应该选静态还是动态

没有永远正确的答案。

### 更适合静态库的情况

- 内部小模块；
- 希望部署简单；
- 不需要运行时替换；
- 不希望单独携带库文件；
- 可执行文件大小可以接受。

你的：

```text
tensor_metadata
request_validation
小型工具模块
```

初期适合静态库。

### 更适合动态库的情况

- 多个程序共享较大实现；
- 库需要独立升级；
- 插件或后端需要运行时装载；
- 第三方SDK本身只提供动态版本；
- 需要控制模块边界和发布方式。

以后推理后端插件可能使用动态库，但需要额外设计ABI和加载接口。

## 33. 常见错误

### 错误1：认为静态库是源代码集合

静态库通常包含已经编译的目标文件，不是简单复制 `.cpp`。

### 错误2：认为动态库不需要链接

常规动态链接仍然需要在构建阶段建立依赖，只是实现代码在运行时装载。

### 错误3：认为静态版完全没有动态依赖

你的业务库可以静态链接，但程序仍可能依赖系统动态库和C++标准库。

### 错误4：把 `.a`交给运行时加载器

静态库主要在链接阶段使用。

### 错误5：只配置include路径，不链接库

可能通过编译但链接时报undefined symbols。

### 错误6：链接成功就认为动态库部署完成

运行环境仍然必须能找到 `.dylib`或 `.so`。

### 错误7：在同一个build目录频繁切换库类型

不利于对比并容易受缓存影响。

### 错误8：明确写STATIC后期待BUILD_SHARED_LIBS生效

明确类型优先，变量不会覆盖它。

### 错误9：消费者直接写库文件路径

现代CMake应优先链接逻辑target。

### 错误10：把INTERFACE库当作动态库

INTERFACE配置target不生成二进制库。

### 错误11：看到动态库能替换就忽略ABI

不兼容的动态库可能导致加载失败或运行错误。

### 错误12：手动添加 `-fPIC`到所有target

CMake会为SHARED库处理常规PIC要求；需要时使用target属性。

### 错误13：把build产物提交Git

`.a`、`.dylib`、目标文件和CMake缓存通常不提交。

### 错误14：只比较文件大小，不运行测试

构建形态改变后仍必须验证业务行为。
